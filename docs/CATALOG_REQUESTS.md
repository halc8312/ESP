# 公開カタログからの依頼受付

公開カタログの「Add」で選択した商品を、生徒の管理画面へまとめて送る機能です。Instagramで在庫・選択肢・送料等を相談するための依頼として扱います。

## 利用の流れ

1. 顧客が同じ価格表内の商品を選択する。希望数量の変更と取り消しが可能。
2. 選択内容を開き、Instagram名、任意の名前・メモを入力する。
3. 送信時にサーバーが価格表の公開状態、所有者の利用状態、各商品の公開対象・在庫・価格を再確認する。
4. 受付番号を顧客に表示し、生徒の `/requests` に未確認の依頼を表示する。
5. 生徒が詳細を確認し、Instagramで連絡する。「確認済みにする」を押すと未確認一覧から外れる。

メール送信、決済、注文確定、在庫予約は含みません。色・サイズ等の希望は顧客がメモに記入し、Instagramで相談します。商品単位の参考価格はバリエーションの最安値となる場合があり、最終的な販売条件を確定するものではありません。

## 保存内容

新規の `catalog_requests` と `catalog_request_items` を追加します。既存の商品・価格表・利用者テーブルへのカラム追加はありません。

| データ | 保存項目・目的 |
| --- | --- |
| 依頼本体 | 所有者、受付番号、価格表・ショップの参照と名称、Instagram名、任意の名前・メモ、受付日時・確認日時 |
| 再送管理 | 送信キーと入力内容のハッシュ。同じ依頼の再送を1件にまとめる |
| 商品明細 | 元商品の参照、受付時の商品名・円価格・希望数量 |

名称・価格はサーバーが公開用の商品情報から確定します。価格が未設定の場合はNULLを保持し、「要確認」と表示します。価格表の個別価格を優先します。仕入先URLやサイト名は顧客への応答に含めません。

元商品・価格表・ショップへの参照は `ON DELETE SET NULL` とし、元データの削除後も依頼の控えを残します。依頼の完全削除画面は設けていません。顧客の連絡先やメモを含むため、保存期間は実運用開始前に運用者と取り決めてください。

## 受付条件と失敗時の扱い

- 1回の依頼は最大50商品、各1〜99点で、送信時の表示在庫を超える数量は受け付けません。
- 他の価格表・利用者の商品、非公開・削除・アーカイブ・在庫なしの商品が含まれていれば、依頼全体を受け付けません。
- 選択後に参考価格が変わった場合は最新の内容を表示し、顧客が確認してから再送します。受付できない商品を自動で除去して送信しません。
- 連打・通信の再試行は同じ送信キーを使います。同じキーで異なる内容を送った場合は競合として扱います。
- 公開送信もCSRF検証を行い、共有レート制限を使います。レート制限用ストアが使えない場合は受付を止めます。
- ブラウザへの保存は価格表ごとの商品選択と送信キーだけです。顧客の名前・Instagram名・メモをCookieやブラウザストレージへ保存しません。
- 生徒は自分宛ての依頼だけを閲覧・確認済みにできます。管理画面のショップ選択に関わらず、自分宛ての全ショップの依頼を表示します。

## 実装の入口

| 役割 | ファイル |
| --- | --- |
| データモデル | `models.py` の `CatalogRequest` / `CatalogRequestItem` |
| DB更新 | `alembic/versions/20260906_0022_add_catalog_requests.py` |
| 受付と検証 | `services/catalog_request_service.py` |
| 公開送信・生徒向け画面 | `routes/catalog_requests.py` |
| 顧客の選択画面 | `templates/catalog.html`、`static/js/catalog_requests.js`、`static/css/catalog.css` |
| 生徒の一覧・詳細 | `templates/requests.html`、`templates/request_detail.html` |
| 回帰テスト | `tests/test_catalog_requests.py` |

DB更新は既存のAlembic起動処理で適用されます。現行の `ADDITIVE_STARTUP_MIGRATIONS` は旧環境救済用のままとし、新表の作成処理を重複して追加しません。

Renderへの反映はマージと別の手動操作です。本番反映後は、承認された確認用データで、公開送信・生徒への表示・確認済み操作を一連で確認してください。マイグレーションのdowngradeは依頼データを削除するため、単なる画面ロールバックとして実行しないでください。

## 検証

依頼受付、価格・在庫の変化、二重送信、利用者の分離、確認済み操作、旧DBからの更新を次のテストで確認します。

```bash
python -m pytest tests/test_catalog_requests.py tests/test_database_bootstrap.py -q
```
